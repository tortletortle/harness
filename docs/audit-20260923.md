## 2. 需要优先处理的问题

### H-01 · P1 · 计划已完成，但 Run 和工作区执行权仍被模型报告生成占用

**直接证据：**

- 专门复现计划：`be257e9d-97fb-488f-802a-2113f866ad27`。
- 约 **0.734 秒**：`GET /api/plan/{id}` 返回 `Completed`。
- 同时：`GET /api/plan/{id}/runs` 仍返回 `Running`；`GET /api/status` 的 `current_execution` 仍指向该计划。
- 执行下一计划：HTTP **409**，`已有任务占用主工作区`。
- 直到约 **68.219 秒**，`current_execution` 才清空。

**定位：** `python/api/runtime/background.py:298–305, 380, 481–518`。代码先写入/广播 Completed，再 `await _generate_final_report(...)`，最后在 `finally` 完成 Run 并释放执行权。交付报告的真实模型延迟进入了任务占用期。

**影响：** UI 显示已完成但下一任务不能开始；Run/Plan 暂时不一致；按 idle 等待的测试超时。默认回归的另外两个 409 是首个超时后产生的连锁失败。

**建议：** 将必需的状态收尾与可选报告生成分开；在释放执行权、终结 Run 后，以可追踪的独立后台任务生成报告。异步报告必须有超时、失败状态及重启恢复策略，避免简单 fire-and-forget 导致产物丢失。

**证据：** `ownership/ownership.json`、`ownership/events.jsonl`、`backend.xml`、`pause-retry.xml`、`p3-baseline-server.log`。

### H-02 · P1 · 真实并发限流未被设计生成入口恢复，配置了 fallback 也直接失败

在本轮多个验收进程同时调用主模型时，网关真实返回：

```text
HTTP 429 rate_limit_error
当前 API Key 的并发请求已达到上限，请等待已有请求完成后再试。
连续重试不会加快响应。
```

随后 `POST /api/design` 返回 **500**，B 验收的 worktree 场景止于设计阶段。

**限定：** 这是本次并行检测负载下触发的上游配额限制，不代表每次单任务都会失败，也不是 worktree 执行器本身失败。主模型已有设计、计划与工具调用成功证据。

**定位：** `python/designer/__init__.py:251–264` 的设计生成直接使用 primary；`python/api/routes/design_routes.py:78–81` 将异常统一包装成 500。计划生成另有 fallback 策略，不能据此推定设计生成也能自动降级。

**建议：** 对 provider 级并发量设队列/信号量；对 429 尊重 Retry-After 并做有上限的退避；按明确规则尝试兼容的备用模型；对客户端返回可辨识的可重试上游错误，而不是通用 500。

**证据：** `live-b/acceptance-b.json`、`live-b/events.jsonl`，请求哈希 `e43fc022f31978392293dc638f302ae45e784cbe96102c719d7566e834299fa8`。

**建议：** 在对应网关确认令牌模型授权/额度，或配置已经实测可用的模型；保存路由后执行真实探测，区别“有密钥”与“该密钥能调用此模型”。不要把密钥写入报告或仓库。

### H-04 · P2 · 标称离线的默认回归仍加载真实配置，易受模型延迟影响

`test_pause_resume_retry.py` 启动子服务。虽然数据库隔离，但服务仍加载仓库的模型配置和可用凭据，并启动配置的 MCP 集成。计划收尾需要生成真实报告，超过该测试 40 秒 idle 等待上限。

独立复跑仍为 **3 failed / 2 passed**。三个失败分别为：

1. `test_skip_step_marks_skipped_and_is_not_executed`：等待 idle 超时。
2. `test_manual_failure_is_not_auto_repeated_and_plan_fails`：上一计划仍占工作区，409。
3. `test_resume_continues_from_first_incomplete_step`：同样因工作区占用返回 409。

**建议：** 将离线回归的配置、凭据加载、MCP 与模型访问彻底隔离；真实集成测试单独标记，并使用独立 fixture 和基于状态的等待。修复 H-01 后仍应保留这层测试隔离。

**证据：** `p3-baseline-server.log`、`backend.xml`、`pause-retry.xml`。

### H-05 · P2（环境）· 文档中的默认 Rust 测试命令无法在当前环境完成


这不是已确认的 Rust 业务代码断言失败。首次 GNU/Zig 补测也因 Zig 不在 PATH 而阻断；随后只在该命令进程内加入已安装 Zig 的路径继续补测，没有修改系统 PATH 或全局 toolchain。

**补测结果：** 本次使用 `stable-x86_64-pc-windows-gnu` + 已安装 Zig 0.16.0，执行 `cargo zigbuild --workspace --tests --target x86_64-pc-windows-gnu --offline`，10 分 45 秒完成编译。随后实际运行本次新生成的 7 个测试程序，**42 passed / 0 failed**（GUI 37，DB/Dispatcher/Logger/Server/Tool Manager 各 1，Common 0）。没有使用 9 月 17–19 日的旧二进制冒充新测试。`sqlx-postgres 0.7.4` 的 future-incompatibility 是另行记录的依赖警告。

**证据：** `rust-test.log`、`rust-gnu.log`、`rust-gnu-path.log`、`rust-binaries.log`。

## 3. 模型契约与质量观察

本轮专用观测器记录 **32 条真实模型请求**：**28 条 HTTP 200、2 条 403、1 条 429、1 条缺终态**。HTTP 200 不等于业务断言通过，例如精确回复探测仍失败。响应中累计报告用量 **105,882 tokens**；这只是已捕获响应的用量，未计入默认回归子服务的隐式调用，也不是完整账单。

| 响应声明模型 | HTTP 200 数 | 成功响应耗时中位数 | 最大耗时 |
|---|---:|---:|---:|
| glm-5.2 | 17 | 66.875 秒 | 108.328 秒 |
| qwen3.8-max | 11 | 15.062 秒 | 70.766 秒 |


- `glm-5.2`：主链路设计/计划成功；普通算术回复正确；真实 function calling 返回 `audit_sum({"a":2,"b":2})`，契约通过。
- `qwen3.8-max`：精确回复探测通过，真实 function calling 通过。
- 主模型对“只回复 AUDIT_OK”的简单探测返回了拒绝性文字，故该单项失败；不能据此断言该模型不可用，后续普通问答和工具调用均成功。
- 本轮主模型短问答也需要约 67 秒。该延迟会放大 H-01 和测试超时问题。
- 个别响应的 `completion_tokens` 高于请求中的 `max_tokens`，并包含 reasoning 用量字段。先按网关的实际计费与参数契约复核，不把这些用量字段直接换算成费用。

## 4. 真实场景与隔离方式

- API 使用真实 FastAPI lifespan、实际数据库实现、工具注册、授权与执行器。
- 设计书/执行计划与 Agent 场景实际访问模型网关；HTTP 观测包装器调用原始发送函数，未伪造响应。
- 专用测试使用 `out/audit-20260923/<场景>/` 下的独立数据库、工作区、缓存和日志。
- worktree 合并仅发生在本轮创建的测试 Git 仓库中，不合并进项目主仓库。
- Checkpoint 的第一次 `exit 7` 是刻意注入的失败；其记录不是产品缺陷。恢复测试计划由脚本构造，并非模型生成。
- C1/C2 并发调度计划由验收脚本构造；不能将这部分说成“模型自动生成了并行 DAG”。
- 备用模型补测只在独立进程中替换角色 primary，不改正式 YAML、密钥或业务源码。
- Web UI 采用本次生产构建 + 独立本地后端，以真实 Chromium 操作。它是 UI 冒烟，不代表已经用鼠标完整走完所有审批/恢复分支。
