## 🎯 测试模块设计

### 模块 1: 推断指令高强度矩阵测试

**目标**: 验证所有工具在所有可能的 inputs 场景下推断指令的正确性

**测试维度**:
- 各工具 × 所有可能的 inputs 组合
- 缺失字段场景
- 多余字段场景
- 字段值类型错误
- 空字符串、None 值
- 特殊字符（中文、emoji、\r\n等）

**测试数量**: 50+ 个用例

**验证点**:
- 推断指令必须在工具声明中
- 工具能够处理推断指令
- 输入验证和错误处理正确

---

### 模块 2: 边界条件测试

**目标**: 验证系统在极端情况下的行为

**测试场景**:

1. **字符串边界**:
   - 空字符串: `""`
   - 超长字符串: 10MB+ 的文本
   - 特殊字符: `\x00`, `\n`, `\r`, `\t`, `\x1a`
   - 国际字符: 中文、日文、emoji、RTL 文本
   - SQL 注入: `' OR '1'='1`

2. **数字边界**:
   - 0 和负数
   - 极大/极小整数
   - 浮点精度问题

3. **路径边界**:
   - 绝对/相对路径
   - 目录遍历: `../../etc/passwd`
   - Windows/Unix 路径混合
   - 不存在的路径
   - 无权限的路径

4. **URL 边界**:
   - 无效 URL
   - 非 http/https 协议
   - URL 过长
   - 特殊字符 URL 编码

5. **时间边界**:
   - 超时值为 0
   - 超时值为负数
   - 极长的超时值

**测试数量**: 40+ 个用例

---

### 模块 3: 并发执行测试

**目标**: 验证系统在并发场景下的正确性、一致性和安全性

**测试场景**:

1. **并发步骤执行**:
   - 5 个步骤并发执行
   - 10 个步骤并发执行
   - 50 个步骤并发执行
   - 检查竞态、死锁、数据不一致

2. **并发计划执行**:
   - 5 个不同的计划同时执行
   - 验证计划隔离
   - 检查全局状态污染

3. **并发 API 请求**:
   - 10 个并发 POST /api/plan/{id}/execute 请求
   - 验证全局执行锁的行为
   - 检查 400 错误是否正确返回

4. **并发数据库操作**:
   - 多个步骤同时写入 steps 表
   - 验证事务一致性
   - 检查"database is locked"错误处理

5. **竞态条件**:
   - execute_step() 和 get_plan() 竞争访问
   - 步骤完成前读取计划状态
   - 检查状态可见性

**测试数量**: 20+ 个并发场景

**验证点**:
- 没有数据损坏或不一致
- 没有死锁或挂起
- 没有内存泄漏
- 错误处理正确

---

### 模块 4: 大规模计划测试

**目标**: 验证系统在大规模数据下的性能和正确性

**测试场景**:

1. **大步骤计数**:
   - 50 步骤计划
   - 100 步骤计划
   - 200 步骤计划
   - 500 步骤计划

2. **大输入数据**:
   - 1MB 的 inputs 字典
   - 10MB 的文本内容
   - 深层嵌套的 JSON 对象

3. **大状态数据**:
   - 每个步骤输出 1MB 数据
   - 计划执行后累积多个 GB 的数据

4. **大结果集**:
   - 返回包含 100+ 步骤的计划
   - 查询包含 1000+ 条日志的结果

**测试数量**: 15+ 个大规模场景

**验证点**:
- 性能是否可接受（检查响应时间）
- 内存使用是否合理
- 数据库查询是否高效
- 序列化/反序列化是否正确

---

### 模块 5: 长时间运行测试

**目标**: 验证系统的长期稳定性

**测试场景**:

1. **连续执行**:
   - 100 个顺序步骤执行
   - 每 10 步查询一次状态
   - 验证没有内存泄漏、文件描述符泄漏、数据库连接泄漏

2. **持续压力**:
   - 1 小时内执行尽可能多的步骤
   - 监控 CPU、内存、磁盘使用
   - 记录性能衰减情况

3. **重复场景**:
   - 相同的步骤执行 1000 次
   - 检查是否有累积错误
   - 验证缓存不会导致问题

**测试时间**: 1-2 小时/场景

**监控指标**:
- 内存占用增长率
- 响应时间趋势
- CPU 使用率
- 数据库连接数
- 文件描述符数

---

### 模块 6: 数据一致性测试

**目标**: 验证多维度的数据一致性

**测试场景**:

1. **状态转移验证**:
   - 验证所有合法的状态转移
   - 验证非法状态转移被拒绝
   - 检查状态转移的原子性

2. **多源数据一致性**:
   - steps 表 vs plans.segments JSON 一致性
   - get_plan() 返回数据 vs 数据库数据一致性
   - 缓存 vs 数据库数据一致性

3. **并发修改一致性**:
   - 并发更新同一个步骤的状态
   - 验证最后一次写入胜利或抛出错误
   - 检查数据是否损坏

4. **事务完整性**:
   - 中途中断步骤执行
   - 验证数据库是否处于一致状态
   - 检查是否有孤立的更新

**验证数量**: 30+ 个数据一致性检查点

---

### 模块 7: 错误恢复和异常处理

**目标**: 验证系统对各种错误的处理

**测试场景**:

1. **工具执行异常**:
   - 工具 execute() 抛出异常
   - 工具返回错误状态
   - 工具超时
   - 工具返回无效的输出格式

2. **数据库异常**:
   - 数据库连接丢失
   - 数据库锁定超时
   - 数据库磁盘满
   - 数据库权限不足

3. **API 异常**:
   - 无效的 JSON 请求
   - 缺失必要字段
   - 字段类型错误
   - 超大请求体

4. **资源异常**:
   - 内存不足
   - 磁盘空间不足
   - 文件描述符耗尽
   - 网络连接失败

5. **恢复验证**:
   - 异常后系统是否可继续工作
   - 异常后数据是否一致
   - 异常是否被正确记录
   - 用户是否收到有用的错误信息

**异常场景**: 25+ 个

---

### 模块 8: 性能基准测试

**目标**: 建立性能基线和检测性能退化

**测试场景**:

1. **单步骤执行性能**:
   - 各工具单步执行时间
   - 平均响应时间
   - P95、P99 响应时间

2. **计划执行性能**:
   - 10步计划执行时间
   - 100步计划执行时间
   - 步骤数 vs 执行时间的关系（应线性增长）

3. **API 响应时间**:
   - GET /api/plan/{id} 响应时间
   - POST /api/plan/{id}/execute 响应时间
   - 步骤数对响应时间的影响

4. **数据库查询性能**:
   - 获取计划信息的查询时间
   - 更新步骤状态的查询时间
   - 日志写入时间

5. **吞吐量测试**:
   - 每秒能处理多少个步骤
   - 每秒能处理多少个 API 请求
   - 不同工具的相对吞吐量

**性能指标基线**:
```
单步执行: < 100ms
计划查询: < 50ms
状态更新: < 20ms
API 响应: < 500ms
```

---

### 模块 9: 安全性测试

**目标**: 验证系统对常见安全威胁的防护

**测试场景**:

1. **SQL 注入**:
   - step_id 包含 SQL 语句
   - inputs 包含 SQL 注入代码
   - 验证是否正确转义和参数化

2. **路径遍历**:
   - file_path 包含 `../../../etc/passwd`
   - 验证是否被正确限制

3. **命令注入**:
   - command 包含 `; rm -rf /`
   - 验证是否被正确转义

4. **资源耗尽**:
   - 大量并发请求导致内存溢出
   - 大量 inputs 导致解析时间过长
   - 验证是否有防护

5. **信息泄露**:
   - 错误消息中是否暴露敏感信息
   - 日志中是否记录敏感数据
   - API 响应中是否泄露内部实现细节

**安全检查**: 20+ 个

---

### 模块 10: 状态机完整性测试

**目标**: 验证系统的状态转移逻辑

**测试场景**:

1. **所有合法转移**:
   ```
   Pending → Running ✓
   Running → Success ✓
   Running → Failed ✓
   Running → Running ✓
   等等所有合法转移
   ```

2. **所有非法转移**:
   ```
   Success → Running ✗
   Failed → Pending ✗
   等等所有非法转移应被拒绝
   ```

3. **转移副作用**:
   - 状态转移后相关字段是否正确更新
   - 状态转移后是否触发正确的事件
   - 状态转移是否被正确记录

**状态转移验证**: 所有可能的转移组合（15+ 个）

## 📌 注意事项

1. **测试隔离**: 每个测试应该独立运行，不依赖其他测试的结果
2. **清理**: 每个测试后应清理临时文件、数据库数据等
3. **可重复性**: 测试结果应可重复，不应有随机性或时间依赖
4. **报告**: 运行后应生成详细的测试报告，包括成功/失败/跳过的统计
5. **性能基线**: 首次运行建立基线，后续与基线对比
